At a glance

The containers below fall into two very different families: contiguous / flat (an array of bytes you can index straight into) and node-based (separately allocated pieces linked by pointers). That distinction drives almost everything about their performance.

"Contiguous" containers are cache-friendly — walking through them sequentially touches nearby memory. "Node-based" containers scatter their elements across the heap, trading raw iteration speed for stable addresses and, in the sorted case, ordering.

struct & class layout

In C++, struct and class are the same kind of thing — the only difference is that members default to public in a struct and private in a class. Both get laid out the same way: fields in declaration order, each one pushed forward to satisfy its own alignment, which is where padding comes from.

std::vector: one contiguous buffer

A std::vector<T> object itself is small and fixed-size — typically just three pointers (24 bytes on a 64-bit system): begin, end, and end-of-storage. The actual elements live in a separate heap buffer that size() elements currently occupy out of capacity() allocated slots.

Why capacity grows the way it does

When size() would exceed capacity(), the vector allocates a new, larger buffer (commonly double the old capacity in libstdc++), copies or moves every existing element over, then frees the old buffer. That's why push_back is only amortized O(1): most calls are cheap, but occasionally one call does O(n) work.

This is also why growing a vector invalidates every iterator, pointer, and reference into it — the elements may have just moved to a completely different address.

std::complex<T>

std::complex<T> is about as simple as a class gets: two values of the same type, stored contiguously with no padding (since both members share the same alignment) — real part first, then imaginary.

Because there's no padding, an array of std::complex<double> is bit-for-bit the same layout as an interleaved array of doubles: [re0, im0, re1, im1, ...]. That's what makes it safe to reinterpret one as the other, which the standard explicitly guarantees.

Ordered vs. hashed associative containers

std::map/std::set keep keys sorted using a self-balancing binary search tree (a red-black tree). std::unordered_map/std::unordered_set give up ordering for average O(1) access using a hash table with chaining.

Every node stores a key (and, for map, a value), plus parent/left/right pointers and a red/black color bit used to keep the tree balanced. This demo inserts plainly without the real rebalancing rotations, just to show the node-and-pointer shape — the real container guarantees O(log n) height no matter the insertion order.
This toy hash is just key % 8 (8 buckets) so collisions are easy to trigger — insert both 3 and 11 and watch them land in the same bucket, chained together. A real unordered_map uses a much better hash and grows/rehashes its bucket array as it fills up.
