Splitting C++ into files

An interactive walkthrough of turning one big .cpp file into headers and sources, why that pays off, how the compiler and linker put the pieces back together, and how the same module gets reused by more than one main() — including a test program. Single self-contained file, no external dependencies.

Why bother splitting one file into several?

A single .cpp file works fine for a 50-line program. Past that, everything you gain by splitting comes from one idea: the compiler only has to redo the work that actually changed, and other programs only need to see what your code does, not how.

Benefit What it means in practice
Faster rebuildsChange one .cpp, only that file (and whatever includes its header) needs recompiling — not the whole program.
ReuseA module compiled once can be linked into several different executables: the real app, a test binary, a benchmark tool.
A clear interfaceThe header is a promise of what's available; callers never need to read the implementation to use it.
Parallel workTwo people can edit two different .cpp files at once without touching the same lines.
TestabilityA test program can link against your module's compiled code without dragging in your app's main().
None of this requires anything exotic — just two file types (.h/.hpp and .cpp) and a rule about what goes in each, covered next.

Splitting a monolith

Start from one file that compiles and runs fine on its own. The goal is to pull out the reusable pieces — the Point type and the two functions — into their own header and source, leaving main behind on its own.

type definition → header function declaration → header function body → source .cpp main() → its own .cpp
Notice Point is defined in full in the header, not just declared — the compiler needs to know a type's complete layout everywhere it's used. Free functions are different: only their signature needs to be visible at the call site, so the body can live in the .cpp.

How the pieces get compiled and linked back together

Each .cpp file is compiled independently into an object file; the linker then stitches the object files together into one executable, matching up every function call with its one definition.

What could go wrong: the one-definition rule

    
A header can be #included into many .cpp files without trouble, because it only declares things. The moment a header contains a full function body instead of a declaration, every file that includes it gets its own copy — and the linker refuses to pick one.

Exactly one main() is allowed per executable. main.cpp and test_main.cpp each define one, so they go into two separate executables that both happen to link the same shapes.o — that's the whole trick.

    

    
This hand-rolled assert-based test runner is the simplest version of the idea; real projects usually reach for a framework like Catch2 or GoogleTest, which give you the same "separate test executable, shared module" structure with much better reporting.
